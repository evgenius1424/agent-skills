# Implement

Execute an agreed spec through integration and verification. The user delegates the outcome; the main agent owns ticket sequencing, workers, review and completion.

1. **Recover context.** Read the spec at the supplied path, repo instructions, relevant decisions and existing ticket evidence. Honor the user's implementation request without asking again to approve tickets. If tickets are absent, create them with [tickets](tickets.md). Verify recorded progress against the current code before resuming; retain completed work. Reconcile interrupted `in-progress` tickets to `done`, `ready` or `blocked` from that evidence, and return unblocked tickets to `ready`.
2. **Establish the baseline.** Inspect the current branch, working tree and checks. Preserve user edits and use the branch containing the required work. Create `spec/<slug>` from that base when useful and consistent with repo instructions; never silently substitute the default branch. Record the base and check results in ticket state. Commit only when authorized, and then include only task-owned changes.
3. **Take the frontier.** Pick `ready` tickets whose blockers are all `done`, lowest number first. Mark a ticket `in-progress`, run its playbook, and record evidence. Mark it `done` only when its criteria pass in the integrated tree. Commit per verified ticket if authorized; otherwise retain the verified working changes.
4. **Delegate independent work.** Use Implementers for independent frontier tickets when it reduces elapsed work, following [delegate](delegate.md). Give each worker the spec, ticket, acceptance criteria, relevant WHYs and exact base. Concurrent writers use isolated worktrees; otherwise use one writer and read-only helpers, or execute sequentially. The main agent alone updates shared ticket/spec state, integrates results, resolves conflicts and reruns affected checks before marking work done. Disjoint module names alone do not prove independence: check shared contracts, generated files and dependencies.
5. **Adapt within the outcome.** Resolve implementation details, missing tests, necessary prefactors and merge conflicts autonomously. Record new consequential decisions and adjust ticket boundaries without asking for approval. If evidence would change agreed behavior, scope or a consequential tradeoff, ask the smallest product question promptly, mark affected tickets `blocked` with the reason and unblocking condition, and continue independent work. Exhaust in-scope alternatives for technical failures. A missing tool or permission gets a precise blocker, not a claim of completion.
6. **Preserve the WHYs.** Put each implemented decision at its durable site under `why`; replace duplicated spec rationale with links. Keep the spec's agreed outcome and acceptance criteria, mark its status and record superseded decisions so future agents can distinguish current intent from history.
7. **Close the whole spec.** Run the Reviewer, including correctness and `guard`, and the Verifier against all acceptance criteria in the integrated tree. Fix supported findings and repeat affected checks/review until no blocking finding remains. Run `learn`. Shipping follows [ship](ship.md) only to the extent authorized.

**Done when** every ticket is `done`, every spec acceptance criterion has passing evidence, consequential WHYs are durable and no blocking review finding remains. A blocked ticket means the spec is incomplete. When no independent work remains, report completed work, exact blockers and how to resume; preserve ticket state for the next session.
